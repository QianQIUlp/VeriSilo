## Verdict rules

This report uses only the following five statuses:

| Status                                     | Meaning                                                                                                                                                                                                                                                                |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Implemented and automatically verified** | The current repository has the implementation, and an automated test or build check directly covers the assertion. A narrow test cannot prove a broader runtime assertion.                                                                                             |
| **Implemented, lab-verified only**         | The implementation exists, but so far there is only controlled manual-environment evidence. The final audit must attach the environment, steps, logs and artifact hashes.                                                                                              |
| **Partially implemented**                  | There are interfaces, UI, partial implementation, test fixtures or roadmap documents, but part of the requirement is missing or the verification is not strong enough.                                                                                                 |
| **Blocked by external conditions**         | The in-repository work already meets the acceptance conditions. The remaining proof depends on real Windows, browsers, virtualization, legitimate images, remote nodes, formal IDs or certificates. This status cannot be used to hide code that has not been written. |
| **Explicitly unsupported**                 | The product boundary deliberately rejects this capability, or the current layer clearly cannot provide it. The UI and documents must state the alternative layer or the reason.                                                                                        |

"Has a button", "has a type", "compiles", "has a mock" and "written into the roadmap" each do not by themselves make something implemented. Every network capability must also distinguish `configured`, `applied` and `verified`.

## Summary of current conclusions

- The current product has independent Profile launch, an encrypted Vault, a complete Silo metadata/archive/delete lifecycle, fixed proxy / external Mihomo, the Companion→Native Host→encrypted Vault network evidence history, and separate definitions of an unsigned candidate workflow and a certificate-secrets-gated signed Windows workflow. The latter has not been run with a real certificate or installer, and it is still not the complete V0.9 desktop platform.
- The desktop app can now export a Silo's non-secret metadata, launch state and Vault network evidence as a local redacted JSON/HTML Blob, after the user explicitly selects one Silo, ticks a confirmation and clicks. The behavior of the real Windows “另存为” ("Save As") dialog has not been verified.
- Automated evidence now covers model validation, Vault passphrase change/backup/restore and schema migration, Silo CRUD / managed directory boundaries, proxy relay, the Mihomo Controller, the Native Host / evidence inbox, frontend command contracts, the SBOM / release policy generators and the extension build audit.
- There is still no real Windows browser E2E, no releasable controlled browser artifact, no real NSIS install/upgrade/uninstall result and no Authenticode-signed artifact. Later `main` has formed the EngineAdapter / EnvironmentBackend / Remote Agent control plane. Their protocols and unit tests cannot replace external runtime evidence.
- The Camoufox standalone Host, the v3 Artifact and the Linux/Windows M0–M2-W accepted evidence were merged into `main` through PR #10. M3-0 accepted the contract-level EngineAdapter/RuntimeManager seam, but the real Host has only a test-only M3-WI seam, and that Gate is still Failed. Without a signed production package, it cannot be called a shipped Managed Identity capability.

### Vault schema compatibility matrix (rechecked without Docker)

The current write format is schema 7. Schemas 1–6 are all supported encrypted import formats. They do not take an implicit deprecation path that fails without a clear reason:

| Source schema | Migration must keep                                                                                      | Safe default for missing new fields                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1             | Silo identity, network configuration, seed reference and 32-byte seed                                    | proxy/Mihomo credentials, network history and remote state are empty.                                                 |
| 2             | schema 1 + proxy credential reference/value                                                              | Mihomo secret, network history and remote state are empty.                                                            |
| 3             | schema 2 + Mihomo Controller secret reference/value                                                      | Network history and remote state are empty.                                                                           |
| 4             | schema 3 + redacted network inbox observation                                                            | Old records missing a runtime binding stay nil/unbound observations. They are not migrated into a current `verified`. |
| 5             | schema 4 + endpoint, pairing/replay ledger, binding, operation result                                    | deletion proof defaults to `None`, orphan receipts are empty.                                                         |
| 6             | schema 5 + authenticated deletion proof                                                                  | orphan receipts are empty.                                                                                            |
| 7             | All current fields, including the orphan receipt that explicitly "does not prove the remote was deleted" | In the current format a missing required field counts as corruption and is not silently filled in.                    |

The final audit must also record: the Windows build number / SKU, the full Chrome/Edge version, the WSL kernel / distribution, the Sandbox / Hyper-V configuration, the Mihomo version, the remote Agent / OS, the verification endpoints, the test start and end times, the Git commit, the build provenance, the SHA-256 of every deliverable and the location of the raw logs.

## Conclusions this baseline cannot claim

- It cannot claim that V0.1–V0.6 are "completed as a whole". Currently only a few narrow capabilities are automatically verified.
- It cannot claim that a proxy setting equals leak-freedom across the whole DNS, WebRTC, TLS or QUIC path.
- It cannot claim that extension scan results have been returned to the desktop, or that the desktop has a per-Silo evidence history.
- It cannot claim that V0.7–V0.9 have been delivered as a complete product. M3-0 contract integration, standalone Camoufox evidence, the Failed/experimental M3-WI and real signed-release acceptance must be stated separately.
- It cannot claim that a VM / remote environment changes the real hardware, and it cannot promise to bypass risk controls or to be undetectable.
- It cannot claim that a releasable Windows installer, production Native Host registration, an SBOM, a reproducible build or an Authenticode signature exists.

This file should be updated after every implementation batch. A status upgrade must be accompanied by direct evidence. The final audit cannot delete unmet items. It can only state that an item was implemented, is blocked by external conditions, or was explicitly excluded by the product.
