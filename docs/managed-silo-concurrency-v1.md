# Local Managed Silo limited concurrency v1

Starting point: `0c93eddc1b8eb8636df58208616f849823d04b36`. The goal is to use two local Camoufox identities at the same time in the same desktop instance and Vault. Profile, process, network, evidence and recovery ownership stay independent. This strengthens Execution/Network/Identity Integrity and Attribution. Capabilities of cold backup v1 that are unchanged are inherited from the [73a6177b acceptance](qa/managed-cold-backup-2026-09-28.md).

## Product and implementation decisions

- Concurrency is allowed only for local Managed Camoufox with Direct or fixed-proxy combinations, at most two. The only production limit is `LOCAL_MANAGED_SESSION_LIMIT` in Rust, and the status interface passes it to the UI. A repeated start, a third session and an unsupported combination are rejected first. They do not close other sessions or downgrade to direct connection. Standard, Mihomo/Clash, WSL and Remote keep their existing single-session boundary.
- Reuse `RuntimeManager` as the single-session owner. The new collection is only responsible for finding the object by Silo, atomic reservation and short-lock snapshots. Each object exclusively owns its Host/browser, Profile lease, relay, health/runtimeId, recovery record and watchdog. The read-only engine package can be shared. Slow I/O occupies only the target object and not the collection or Vault lock. A status read may use the last snapshot published by that object. It cannot borrow another object's evidence.
- The old `runtime/browser-session.json` is still read. New records are in the same directory, named per Silo. A corrupt, unknown or not-yet-recovered record is kept and blocks an unsafe start. A restart does not promise to reopen web pages automatically.
- `DesktopStatus.sessions` is `{ siloId, activation, websiteIdentity? }[]`. Ownership does not depend on `activeSiloId`, which is cleared after a stop. `managedSessionLimit` is the central limit. The old `activation` keeps the original object when there is exactly one managed session, and is `null` when there are multiple sessions. The first entry must not pose as the single state. When there is no session, the idle/old single-session end semantics are kept.
- New Tauri `list_runtime_sessions` / `get_silo_runtime`, and HTTP `GET /v1/sessions` / `GET /v1/silos/{id}/runtime`. Start, stop, re-observe and page actions always name a target. The CLI supports both collection and target queries. A target-less single query from Native Host/Companion is explicitly unavailable when ambiguous. A target query is bound to the Silo/runtime and does not accept evidence with the wrong ownership.
- UI selection is independent of the run collection. It tracks busy state and async responses per Silo. Switching the selection does not change the runtime identity. Locking the Vault clears all sensitive UI state.
- The existing global lifecycle reservation becomes a global write barrier / target read barrier, and the target object serializes its own operations. Vault lock, whole-Vault restore, engine maintenance and exit handle all sessions. A single-Silo cold backup only checks that the target is stopped and not occupied. Restoring A while B is running cannot clear B. The backup format and cryptography do not change. Vault lock keeps its existing semantics: all sessions revoke their decryption credentials and current page observations. Sessions that depend on a proxy relay fail closed. A Direct browser is not promised to be force-closed. After the lock, the page API is unavailable. Exit closes all local Managed sessions.

## Acceptance and boundaries

One integration task completes design, code and acceptance. Commit the shared contract in small steps first. After the full implementation, run the necessary full integration matrix once. Later fixes revalidate only what changed or failed. Real native Windows, a disposable named Vault and the pinned Engine verify: isolation of persistent Cookie/localStorage/IndexedDB with both sessions active; independent re-observation, stop and restart; routing through a locally controllable fixed proxy and fail-closed on a single-side fault; cold restore of A while B is running; and the limit, duplicate start, lock, exit and restart-recovery ownership. The UI Preview verifies only interaction, selection, late responses and error states.

A local proxy test does not derive the public network exit or a complete absence of leaks. It keeps the required exit observation that fixed-proxy creation already has. It adds no production dependency, does not change the Host package, does not change global ACLs, does not rebuild the core and does not open RC/installer/release. If any of these boundaries really must change, first report the specific necessity.

Each piece of work maps to a clear product problem or a necessary uncertainty and inherits valid evidence. Repairs are followed by the lowest sufficient validation. Without new evidence or a new hypothesis, do not retry expensively. A historical Sandbox and the release flow are not points to resume from. Completion must be judged by direct evidence of the necessary product behavior. A failed attempt is kept as is, and a new attempt is produced only after a causal blocker is fixed. Finally, run verify/check, publish the task branch and fast-forward publish the baseline. Force push and advancing main are forbidden.
