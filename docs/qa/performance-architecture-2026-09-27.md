## Development directory failure and verification boundary

A copy of the same package inside the worktree had failed to start earlier. The Juggler pipe sent and received normally. The GPU child process failed to start three times, and TargetRegistry reported `gBrowser never populated`. Playwright could not get the first Page, and the Host stopped at `launch_persistent_context` before the identity probe ran. That is how the problem of the CLI timing out before the background was found and fixed. A Vault list read during that failure still completed in 52 ms.

The minimal native comparison still failed after bypassing the product Host/Job and removing the identity configuration and product preferences. A comparison independent of the outer Job of the command runner also failed. But the same driver with the browser in the installed directory created a page in about 8.795 seconds. The 504 files of the two browsers are identical by SHA-256. After copying the current debug app and the same package to a separate LocalAppData directory and registering with a new Vault, the full product path produced the results in the table above.

What is kept is therefore an **unexplained limitation tied to the run directory**. There is not yet enough evidence to name the ACL, Defender, path length, a DLL or the OS version as the root cause. The browser sandbox or Job is not weakened on this basis, and the whole host is not declared unable to run. Static PE inspection found no missing regular/delay imports and no missing non-API-set exports. It cannot rule out dynamic-loading problems. The launch Job in this round only moves existing logic and adds no layers or restrictions.

**Follow-up status (2026-09-27):** the [directory ACL causal comparison](managed-engine-directory-acl-2026-09-27.md) has narrowed the "unexplained limitation" above to an inherited-DACL development limit of the current Codex sandbox/worktree. With the same path, the same owner and the same 504 files, changing only the DACL turned page creation from a 60-second failure into a 5.344-second success. The specific ACE, Windows API error or deeper mechanism is still not identified. The product path in a separate LocalAppData directory in the normal user context passed. This problem is not treated as a current product blocker or a default follow-up investigation task.

One start after the migration still referenced the worktree package path registered by the old Vault. It cannot be counted as a failure of the new directory. The driver log of the later new Vault clearly records the actual new path. In this machine's Codex MSIX environment, it resolves to `Packages/OpenAI.Codex_2p2nqsd0c76g0/LocalCache/Local/VeriSiloDev/performance-37abe4`. To verify a migration, first check the real engine binding. Do not judge the package path only by where the desktop exe is located.

The raw failure logs and results are kept in the ignored directory `artifacts/performance-goal/` of this worktree. The success evidence is in the table above. These limitations are not disguised as a general environment fix, and no permanent diagnostic framework was added for this local directory problem.
