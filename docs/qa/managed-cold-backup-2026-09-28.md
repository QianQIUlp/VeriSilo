# Managed Silo cold backup restore: native Windows development acceptance

> Translated from the original Chinese on 2026-11-10. The original text is in Git history at commit 1cf0f29. For historical evidence, the original wording governs if the two differ.

Status: **native Windows development acceptance passed**. The final result is `73a6177b`. The three earlier independent attempts are also kept below. Their failures, and a digest defect found later, are not rewritten as success.

## Question to answer

On the same Windows machine, with the same normal user and the same named Vault, can a stopped Managed A be backed up into an encrypted archive that contains its Profile, Identity Artifact, Engine binding and Silo configuration? After A's browser data is then overwritten, does restoring the original A read back the persistent Cookie, localStorage and IndexedDB values from the time of the backup, while B is preserved? Are a wrong archive hash and a wrong passphrase both rejected without changing the current A/B?

The runner is [`tests/windows/managed-cold-backup-acceptance.mjs`](../../tests/windows/managed-cold-backup-acceptance.mjs). It drives browser pages through the real Local API and the existing [`loopback-server.mjs`](../../tests/windows/fixtures/loopback-server.mjs). The test uses a one-time `coldbk-*` Vault, Direct network, a local `127.0.0.1` site and random synthetic markers. It first backs up the stopped A, then overwrites A's three kinds of persistent markers, confirms that the rejections do not break anything, restores and reads back the original markers, and finally starts B and reads back B's markers. This round draws no conclusion about the cold-start behavior of sessionStorage or session Cookies. The Profile directory is managed by the product. The runner does not copy, delete or modify Profile files directly.

The acceptance run uses a separate development program directory under the normal user's LocalAppData, with file hard links to the existing Engine package. It does not change package files, global ACLs, the default Vault, the installed product or the historical performance development directory. It builds only the debug `verisilo.exe` and `verisilo-cli.exe`. The CLI background service does not need a Vite/UI server. The runner verifies `telecaster\qiu`, a clean candidate worktree and an explicit source SHA, and records the SHA-256 of the two debug exes and of the Engine manifest. The archive, Vault and results stay in this run's dedicated directory for diagnosis. The report stores no passphrase, Local API token or fixture token.

Success boundary: the archive/Silo/Artifact digests returned by the three APIs agree. A's original markers are read back after the overwrite and the cold restore. B's metadata and markers are unchanged. Both wrong-restore cases are rejected, and A's overwritten markers are still readable. All Managed sessions stop normally. A failure keeps the original `result.json`, and a retry with a new run ID happens only after fixing a cause that the evidence supports. When the browser cannot start, first check the actual account and Engine path. Do not count the existing DACL restrictions of the worktree or the Codex sandbox as a product regression.
