## What was executed

The native runner is [`tests/windows/managed-concurrency-acceptance.mjs`](../../tests/windows/managed-concurrency-acceptance.mjs). It requires the exact committed source SHA, a clean worktree, `telecaster\qiu`, a one-time `managed2-*` Vault, and the debug `verisilo.exe`, `verisilo-cli.exe` and the existing fixed Engine package (manifest SHA-256 `7bfb701935221b523027738d0c7abaa386851471e99f08eec7eb2bf09917278e`) in a separate development program directory under the normal user's LocalAppData. It does not overwrite the old program directory or change system ACLs. The program, CLI and Engine manifest hashes are written to the raw `result.json`. Results stay in a one-time output directory. A failure keeps its raw state, and the run is not simply repeated with unchanged inputs.

`--ui-checkpoint` is passed explicitly only when a native UI manual switching check is needed. A background continuation by default does not open a desktop window or wait for the UI. After the two active sessions are running, this optional mode uses the CLI to open the desktop of the same instance and writes `<outputDir>/ui-checkpoint.json`. It contains only the two Silo IDs, the runtimeIds, the service PID, the candidate SHA, a random checkpointId and the path of the continue file. It contains no API token and no Vault or proxy passphrase. After the checker switches the selection on that desktop and records the UI evidence, the checker atomically writes `<outputDir>/ui-continue.json` with the content `{"schema":"verisilo-managed-concurrency-ui-continue/v1","checkpointId":"<value from the checkpoint>","result":"passed"}`. On failure it writes `"failed"`. The first direct acceptance run waits at most ten minutes. The P/Q dual-active check of `--continue-after-backup` waits at most 90 seconds. After the continue file arrives, the runner checks both runtimeIds and running states against the same API again. If the latter times out or fails, it records only that the UI is unconfirmed, and the backend C/E steps continue. Waiting time does not count as a pass. The late-response and error display of UI Preview is verified separately.

The local site reuses [`loopback-server.mjs`](../../tests/windows/fixtures/loopback-server.mjs) and reads and writes Cookie, LocalStorage and IndexedDB with random synthetic values. The fixed-proxy acceptance uses two independent [`loopback-connect-proxy.mjs`](../../tests/windows/fixtures/loopback-connect-proxy.mjs) instances. They listen only on `127.0.0.1`, map the reserved test address `198.51.100.9` to the test site, and separately record the CONNECT requests that the browser operation token actually passes through. No packet is sent to that reserved address. The proxies pass through only the network-exit observation requests `ipwho.is:443`, `api.ipify.org:443` and `api.ip.sb:443`, which the existing Host needs at startup. All other targets are rejected. This observation only satisfies the startup rule of the original product. The real public network exit of a proxy is not inferred from a same-machine local proxy experiment. The allow/reject and routing self-checks of the proxy fixture are done by Node built-in tests.

## Direct acceptance criteria

| Product question                   | Native criterion                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dual-active and identity isolation | A and B are `running` at the same time in the same Vault with Direct. Their `runtimeId` values differ. A still answers per-Silo status and page requests while B is starting slowly. Each side reads back its own different persistent Cookie, LocalStorage and IndexedDB.                                                                                                                                                                                                                                                                                        |
| Independent management and limit   | A third Managed Silo and a repeated start of A are rejected, and the existing A/B keep running. Re-observing A does not change B's recent-run binding. After A is stopped, B's page is still readable. After A is restarted, it keeps the original Artifact and persistent data.                                                                                                                                                                                                                                                                                  |
| Proxy routing and failure          | Two fixed HTTP proxy sessions P/Q run at the same time. The two independent CONNECT fixtures each record only the page operation token of their own session. After P's upstream is killed, the local site receives no direct-fallback request from P, and Q can still read back its data through its own proxy. Direct A and proxy Q can run at the same time.                                                                                                                                                                                                    |
| Cold restore combination           | While B is alive, a backup of the running B is rejected. The stopped A completes backup and digest inspection. An overwrite of the running A is then rejected. After A is stopped, an explicit restore brings the overwritten A back to its original persistent values, and B's page and recent-run binding are kept.                                                                                                                                                                                                                                             |
| Global operations and restart      | Locking the Vault rejects all active page operations. After unlock, both sessions can still be managed under the original rules. Quitting the app cleans up both sessions. After a service restart, the per-Silo status and recent run still belong to A/Q. They must not show a Silo as still running or borrow evidence from another Silo. Locking is not interpreted as meaning that a Direct browser necessarily exits. Compatibility with the old single-session API/CLI and the old restore format is covered by the corresponding focused automated tests. |

`matched` only means that the current identity matches. It cannot be raised to `verified`. The recent-run record is history. When comparing B, check the runId, runtimeId and the Profile/Artifact/Network Policy bindings. Do not freeze timestamps that a healthy thread may legitimately update. For proxy failures, that the page did not go direct and that the other session stays available are direct observations. The local experiment does not prove the public network exit, complete DNS/WebRTC leak-freedom, or the availability of a real proxy service.

A runtime query of Native Host protocol 2 can pass `siloId` explicitly. With no target and two sessions, it returns `unavailable`. The Companion therefore keeps only the local observation and does not treat either session as the single active identity. Submitting and reading staged network evidence both validate `siloId` and `runtimeId` together. An old snapshot without a `sessions` field is still interpreted as a single session. The protocol version and the backup format are unchanged.
