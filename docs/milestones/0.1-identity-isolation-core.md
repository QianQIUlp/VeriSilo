# 0.1 source milestone — Identity isolation core

- Milestone date: 2026-08-04
- Code baseline: `main@527516ab65f49061ccac67287fa96fa93f006421`
- Distribution status: source milestone only
- Tag: not created
- GitHub Release: not created
- Signed installer: not published

## Why this milestone exists

VeriSilo's identity-isolation core is no longer a set of separate experiments. On `main`, the desktop app, the browser launcher, the network coordinator, the Native Host, and the optional Companion now form one connected Windows product skeleton with an explicit lifecycle and an explicit evidence model.

This milestone is a public, citable checkpoint for that state. It answers three questions for anyone reading the repository: what the product is, what has actually closed in source, and which capabilities remain gated or unfinished. It is intentionally not a release: no Git tag, no GitHub Release, no signed installer, and no browser-store listing are created here.

## Closed in source

The following groups describe what the current `main` baseline contains. "Closed in source" means the implementation, interfaces, and repository-level gates exist and can be inspected; it does not by itself mean every real Windows machine has passed hands-on acceptance.

### Silo lifecycle and encrypted Vault

- Tauri v2 desktop foundation with an Argon2id-protected local Vault: a password-derived wrapping key protects a random AES-256-GCM data key.
- Passphrase rotation, encrypted envelope backup and restore, schema migration.
- Explicit Silo create, edit, archive, restore, and permanent-delete lifecycle controls with a run-time refusal to mutate running Silos.
- Vault protects Silo metadata and optional network credentials, not the browser-owned profile files.

### Independent browser state

- Every Silo receives a separate, managed `--user-data-dir`.
- Cookies, storage, cache, service workers, permissions, and history remain browser-owned files inside that directory.
- The default browser Profile is never selected, imported, cloned, or modified.

### Runtime identity binding

- A single-active-Silo runtime model: launching a Silo binds it to one explicit runtime identity.
- RuntimeManager tracks the exact PID tree and refuses force-killing unrelated browser processes.
- Restart and lock-file recovery keep stale runtimes from being reused.

### Per-Silo network identity

- Direct network profile, fixed HTTP/SOCKS proxy profile, and external Mihomo/Clash-compatible adapter are selectable per Silo.
- Proxy credentials never reach the browser: the browser connects to a random loopback relay owned by the desktop process.
- Long-lived Silos keep a fixed endpoint or fixed Mihomo node; rotation is an explicit user action, never background randomization.

### Fail-closed paths

- Required-proxy launch configurations reject `direct://`, disable implicit loopback bypass, map ordinary hostnames away from the host resolver, disable QUIC bypass, and restrict non-proxied WebRTC UDP.
- Endpoint, credential, node, or controller drift revokes the current runtime's relay so the browser only sees network failure instead of silently returning to the host network.

### Companion and Native Host evidence

- A Manifest V3 Companion observes page context, explains capability limits, and exports local redacted reports on explicit user confirmation.
- The Native Host validates protocol, active-Silo binding, and freshness; user-initiated network evidence is labeled `extension_asserted` / `observed`, not process-authenticated.
- Evidence is persisted in the encrypted Vault with explicit DNS, WebRTC, and QUIC coverage limits; reports are not synced to any VeriSilo service.
- The desktop isolation boundary works without the extension installed.

### Windows desktop productization

- The desktop UI has moved from internal capability panels to task-oriented product screens for Silo overview, create, edit, settings, and evidence history.
- Network profiles, Vault state, and runtime status are surfaced with the configured / applied / verified vocabulary.

### Release and supply-chain gates implemented in source

- Reproducible lockfile SBOM generation, SHA-256 and provenance tooling.
- Native Host current-user installer hooks with clearly separated unsigned and certificate-secrets-gated signed workflows.
- Candidate builds emit a lockfile-to-package-metadata license evidence report; every component remains pending explicit human license review.
- Windows desktop, extension, engine, environment, and remote-provider verification scripts and their self-tests exist in the repository.

## Evidence boundary

Evidence in this milestone is layered, and the layers are not interchangeable:

- **Repository implementation**: code, schemas, contracts, UI, and scripts exist on `main` and can be reviewed. Having an interface, a UI, or a mock is not a real-machine result.
- **Automated verification**: repository-level tests and static gates pass in the environments where they were run. They do not cover Tauri startup, WebView2, NSIS, or real Windows browser sessions by themselves.
- **Hands-on Windows evidence**: genuine Windows 10/11 × Chrome/Edge results are tracked separately in the acceptance records. Any such item that has not been executed and saved stays pending.
- **External conditions still blocking release**: signed engine artifacts, supported Windows/virtualization hosts, legal guest images, store extension IDs, real certificate secrets, and a real remote Provider remain outside what source code alone can prove.

## Not included in this milestone

- No signed public installer.
- No browser-store distribution.
- No trusted bundled controlled browser-engine artifact shipped with the product.
- No complete TLS or QUIC rewrite on the stock Chrome/Edge path.
- No real-hardware impersonation.
- No undetectability claim.
- No fraud or policy-bypass capability.
- No universal Worker or Service Worker control.
- No default public VeriSilo cloud.
- No guarantee that every Windows, virtualization, or remote Provider combination has passed real-machine acceptance.

## Next milestone — Browser-visible identity consistency

The next phase focuses on keeping one Silo's browser-visible identity stable and consistent across contexts, not on unbounded randomization:

- Stable per-Silo identity across restarts.
- Constrained identity templates with explicit rules instead of blind random values.
- Window, iframe, Worker, header, and network observations that do not contradict one another.
- Controlled-engine verification with direct evidence per field.
- An `observe → apply → verify → restore` loop with per-site fallback.
- A compatibility matrix covering dedicated test pages, fingerprint-collector-style probes, and contradiction rules.
- No undetectability claim, and no promotion of stock-browser fingerprint control.
